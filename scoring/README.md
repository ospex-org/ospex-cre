# scoring

The v3 scoring program's readers and its feed table. For one game, it reads each of the four
feeds and says, feed by feed, whether the feed was silent, answered without a final, or
answered with a final and its two scores. Deciding what those readings add up to (the
agreement rule, the hour-24 void, the dispute record and day 7) is the next piece, built on this
one. This folder imports nothing from Chainlink, so the Chainlink workflow and the open path's
sealed machine run the same files.

## The feed table

[`src/table.ts`](src/table.ts) is the one file that names a feed. Everywhere else, in the
code, the fixtures, the tests and every reading, a feed is its seat:

| Seat | Role |
|---|---|
| 1 | counts |
| 2 | counts |
| 3 | counts |
| 4 | the spare, asked on every run |

A feed keeps its seat in every league. Six leagues are offered (`nfl`, `nba`, `mlb`, `nhl`,
`ncaaf`, `ncaab`), each with all four seats. The table is frozen at load and is part of the
program's fingerprint. The only things handed in at runtime are the game (read from the chain),
the run's clock, a transport, and each seat's key; a test shows that none of them changes which
seats are asked.

## How a game is read

Seats 1, 2 and 4 are read by team and window. Seat 3 is read by its creation hint: its results
carry points and status but no team names and no game time, and its board, which has both, drops
a game once the game is final, so the hint is the only thing that ties a result to a game.

* **By team.** A feed's record is the game only when its two teams resolve to the game's two
  teams, in either order. Points come back by team, never by the feed's home or away slot, so a
  feed that lists the teams the other way round still reads right. Every name a feed gives a team
  must resolve to that one team; a name the lists don't know, beside one they do, leaves the team
  unresolved. No reader takes a city as a team's name.
* **The team lists** ([`src/teams/`](src/teams)) are generated by `capture/teams.ts`. A spelling is
  an alias only when a seat's own list carries it (the team lists of seats 1, 2 and 4, and seat 3's
  board) and one reviewed identity joins it to exactly one team: the team's own name on seat 1's
  list, or a hand join in `capture/joins.json`, grouped by seat and league with the reason each
  group's spellings are that team. Nothing shortens a name to make it match: "Colorado College" is
  not the Colorado Buffaloes. A name that matches no team, or two, joins nothing, and so does a name
  a school outside the league's teams also carries on seat 1's list, with one reviewed exception
  (Georgia, whose namesake there is not a school). College football and basketball share each
  school's spellings. `capture/teams-report.txt` lists every hand join and every name that joined
  nothing.
* **The window.** A record counts only if the feed's own game time for it is inside
  `[start, start + n)`, the game's n and nothing else. The start instant is in; the end is open,
  so a game at the same clock time the next day is out. The start is the scheduled start, taken
  from the counting seats when the game is verified; seat 4's own time is the actual start, which
  only ever serves seat 4's own window check.
* **Only one.** Without a hint that names it, a record is the game only when nothing else in the
  answer could be: no other record of the two teams inside the window (a doubleheader, or the next
  game of a series), no record inside the window with one of the game's teams beside a name the
  lists don't know, and no such record without a game time. Otherwise the seat is silent. A record
  whose two names both fail to resolve names neither team and is ignored.
* **Hints, seats 1, 2 and 4.** A creation hint names a feed's own id for the game. If the feed has
  a record under that id with the game's two teams, that record is the game: inside the window it
  is read, and outside it reads "no final" and nothing else is searched. A hint the feed doesn't
  have, or one under other teams, is dropped, and the game is found by its teams. In a
  doubleheader or a series, a hint is what lets a seat read the earlier game.
* **Seat 3, by hint.** One request: the feed's result for the game's seat 3 id. The hint rides in
  the creation event on chain, so anyone can re-run the match while the feed answers for that id:
  in the answers saved on 22 Oct, a result about four days old answered, and ids 78 to 156 days
  old answered nothing (the feed says five days). With no team names or time to read, seat 3's
  points are the feed's own home and away, bound to the game by the hint; checking that binding
  against the feed's board while the game is listed belongs to verification. No hint, two
  different hints, or a hint that is not a seat 3 id, and seat 3 is silent without asking.
* **Final or not.** Each reader maps its feed's status to final or not final, and a final also
  needs the feed's own sign of a whole game: at seats 1 and 2 the period count reached the league's
  regulation (or, where seat 1 fills in no period count, every quarter scored); at seat 3
  `FinalType` "Finished"; at seat 4 `completed`. Postponed and cancelled are recorded where a feed
  has them and decide nothing. Each reader's header says its feed's rule.
* **One game under two dates.** A feed can list the same record under two of the dates asked for.
  Identical copies are one record; if the record changed between the two requests, the later answer
  stands, unless the copies name different teams or the earlier was already final.
* **Silent.** A feed is silent when it can't answer about the game: no key, a refused or failed
  request (a 401 from a league the seat's plan does not cover reads `http 401`, so the reason
  travels with the reading), an answer that doesn't parse, a record with no game time, a final
  without points, more than one record that could be the game, a date whose answer came back empty
  when the game was not found, a game older than seat 4 keeps, and, at seat 3, no usable hint, no
  result for it, or a hint naming a row for part of the game. Silent is never turned into "no
  final".

## Requests per game

One read of one game, measured over every saved case: seats 1 and 2 ask once per filing date and
page, 2 to 4 requests (three dates for most windows; four when one date's answer runs to two
pages); seat 3 asks once, or not at all without a hint; seat 4 asks once (two credits on its plan),
or not at all past 66 hours. The cap is 12 requests per seat per game (`MAX_REQUESTS` in
`src/run.ts`).

## Running

```bash
bun install --frozen-lockfile
bun test          # no key, no network: every answer comes from fixtures/
bun run typecheck # src/ loads no runtime types, so it cannot name process, fetch or Bun
```

To see one game read, seat by seat, from the saved answers:

```bash
bun run replay --list                                  # the saved cases and their clocks
bun run replay --case "mlb doubleheader, game 1"       # one case, at its own clock
bun run replay --game game.json --at 2026-10-23T03:32:00Z
```

A game file holds what the chain holds for a game: `league`, `home`, `away`, `start` (an ISO time
with its zone, or unix seconds), `n` in seconds, and `hints` (`[{ "seat": 3, "id": "..." }]`).
A request the saved answers don't hold is listed, and that seat reads silent.

## Fixtures

`fixtures/` holds the feeds' answers exactly as they came back, one file per request, and
`fixtures/index.json` records each one's seat, path, status, size, SHA-256 and capture time. The
index keeps paths, never hosts or keys. A test checks every file against its hash, so an edit or a
line-ending conversion fails the suite; `.gitattributes` marks the folder `-text` for that reason.

A request asked more than once keeps every answer. Each test case reads at its own clock and is
served the latest answer captured at or before it (to the second), so one game can be read not
final at one clock and final at a later one, by the same requests, and a league a seat once
refused reads `http 401` at the clock of the refusal and answers at a later one.

## Re-running the capture

With each seat's key in `OSPEX_SEAT1_KEY` to `OSPEX_SEAT4_KEY`:

```bash
bun capture/capture.ts <plan.json>   # runs the readers live and saves what they ask for
bun capture/teams.ts                 # rebuilds src/teams/ from the saved team lists
```

The capture never prints or saves a key. It paces each seat to its plan and prints the calls it
made.
