# scoring

The v3 scoring program. For one game, it reads each of the four feeds and says, feed by feed,
whether the feed was silent, answered without a final, or answered with a final and its two
scores. Then it decides by one fixed rule what those readings add up to: a start, a score, the
hour-24 void, a dispute record, a day-7 result, or nothing yet. It builds the one report shape
the games set takes. This folder imports nothing from Chainlink, so the Chainlink workflow and
the open path's sealed machine run the same files. Its entry point is `src/program.ts`.

## The feed table

[`src/table.ts`](src/table.ts) is the one file that names a feed. Everywhere else, in the
code, the fixtures, the tests and every reading, a feed is its seat:

| Seat | Role |
|---|---|
| 1 | counts |
| 2 | counts |
| 3 | counts |
| 4 | the spare, asked on every run |

A feed keeps its seat in every league. Six leagues are offered (`nfl`, `nba`, `mlb`, `nhl`,
`ncaaf`, `ncaab`), each with all four seats. Nothing here shows that the four feeds draw on
independent sources upstream: agreement across seats guards against one feed's error, not against
an error several feeds copied from one source. The table is frozen at load and is part of the
program's fingerprint. The only things handed in at runtime are the game (read from the chain),
the run's clock, a transport, and each seat's key; a test shows that none of them changes which
seats are asked.

## How a game is read

Seats 1, 2 and 4 are read by team and window. Seat 3 is read by its creation hint: its results
carry points and status but no team names and no game time, and its board, which has both, drops
a game once the game is final, so the hint is the only thing that ties a result to a game.

* **By team.** A feed's record is the game only when its two teams resolve to the game's two
  teams, in either order. Points come back by team, never by the feed's home or away slot, so a
  feed that lists the teams the other way round still reads right. Every name a feed gives a team
  must resolve to that one team; a name the lists don't know, beside one they do, leaves the team
  unresolved. No reader takes a city as a team's name. A college team the feed's own record gives
  no conference (seats 1 and 2 give none to a team outside Division I) is no team of the league,
  whatever its name.
* **The team lists** ([`src/teams/`](src/teams)) are generated by `capture/teams.ts`. A spelling is
  an alias only when a seat's own list carries it (the team lists of seats 1, 2 and 4, and seat 3's
  board) and one reviewed identity joins it to exactly one team: the team's own name on seat 1's
  list, or a hand join in `capture/joins.json`, grouped by seat and league with the reason each
  group's spellings are that team. Nothing shortens a name to make it match: "Colorado College" is
  not the Colorado Buffaloes. A name that matches no team, or two, joins nothing, and so does a name
  a school outside the league's teams also carries on seat 1's list, with one reviewed exception
  (Georgia, whose namesake there is not a school). College football and basketball share each
  school's spellings. `capture/teams-report.txt` lists every hand join and every name that joined
  nothing. A league's teams are seat 1's current entries: every team on its NFL and MLB lists; on
  its NBA and NHL lists, the teams with a current conference (the lists also carry defunct and
  overseas teams); in college basketball, the Division I schools (the entries with a conference);
  in college football, every entry that names a school.
* **The window.** A record counts only if the feed's own game time for it is inside
  `[start, start + n)`, the game's n and nothing else. The start instant is in; the end is open,
  so a game at the same clock time the next day is out. The start is the scheduled start, taken
  from the counting seats when the game is verified; seat 4's own time is the actual start, which
  only ever serves seat 4's own window check.
* **Only one.** Without a hint that names it, a record is the game only when nothing else in the
  answer could be: no other record of the two teams inside the window (a doubleheader, or the next
  game of a series), no record inside the window with one of the game's teams beside a name the
  lists don't know, no such record without a game time, and no record the lists can't place inside
  the window and earlier than it. Otherwise the seat is silent. A record the lists can't place has
  neither side resolved (a name the lists don't know, or a team the feed marks outside the league),
  or one of the game's teams beside a team marked outside. Earlier in the window, it may be the game
  itself, listed in a way the lists don't know, and the record after it the two teams' next game. At
  the same instant or later, or with no time, it doesn't stop the read. A record whose two names
  both fail to resolve also keeps the seat from saying the game is absent while it is inside the
  window: it could be the game, respelt.
* **Hints, seats 1, 2 and 4.** A creation hint names a feed's own id for the game, and only chooses
  among records that pass both tests above: the game's two teams, and a time inside the window. A
  hinted record that passes both is read, whatever else is in the window; one that fails either is
  never read. A hint the feed doesn't have, or one under other teams, is dropped, and the game is
  found by its teams. A hinted record of the two teams outside the window leaves the seat silent
  while anything inside the window could be the game, and otherwise is dropped too. Two different
  hints for one seat leave it silent. In a doubleheader or a series, a hint is what lets a seat
  choose between the games inside the window; verification checks only seat 3's.
* **Seat 3, by hint.** One request: the feed's result for the game's seat 3 id. The hint rides in
  the creation event on chain, so anyone can re-run the match while the feed answers for that id:
  in the answers saved on 22 Oct, a result about four days old answered, and ids 78 to 156 days
  old answered nothing (the feed says five days). With no team names or time to read, seat 3's
  points are the feed's own home and away, bound to the game by the hint; checking that binding
  against the feed's board while the game is listed belongs to verification. No hint, two
  different hints, or a hint that is not a seat 3 id, and seat 3 is silent without asking.
* **Final or not.** Each reader maps its feed's status to final or not final, and a final also
  needs the feed's own sign of a whole game: at seats 1 and 2 the period count reached the league's
  regulation (or, where seat 1 fills in no period count, every quarter scored); at seat 3
  `FinalType` "Finished"; at seat 4 `completed`. A record that says final short of that reads
  silent: neither a final the reader can take nor a game the feed calls unfinished. Postponed and
  cancelled are recorded where a feed has them and decide nothing. Each reader's header says its
  feed's rule.
* **One game under two dates.** A feed can list the same record under two of the dates asked for.
  Identical copies are one record; if the record changed between the two requests, the later answer
  stands, unless the copies name different teams or the earlier was already final.
* **Silent.** A feed is silent when it can't answer about the game: no key, a refused or failed
  request (a 401 from a league the seat's plan does not cover reads `http 401`, so the reason
  travels with the reading), an answer that doesn't parse, a record with no game time, a final
  without points or short of a whole game, more than one record that could be the game, two
  different hints, a date whose answer came back empty when the game was not found, a game older
  than seat 4 keeps, a clock that isn't a number, and, at seat 3, no usable hint, no result for it,
  or a hint naming a row for part of the game. Silent is never turned into "no
  final".

## Requests per game

One read of one game, measured over every saved case: seats 1 and 2 ask once per filing date and
page, 2 to 4 requests (three dates for most windows; four when one date's answer runs to two
pages); seat 3 asks once, or not at all without a hint; seat 4 asks once (two credits on its plan),
or not at all past 66 hours. The cap is 12 requests per seat per game (`MAX_REQUESTS` in
`src/run.ts`); a window of ten days or less always fits in it at one page a date, and a longer
one can leave seats 1 and 2 silent for want of requests.
Each game is read on its own: a slate of games costs the sum.

## What the readings decide

[`src/rule.ts`](src/rule.ts) holds the agreement rule, and every count in it is a constant
inside the fingerprint. For a game whose start is written:

* **Inside n**, every counting seat answers with a final, and the finals are the same: the same
  points for both teams. A silent counting seat blocks. So does one that hasn't answered with a
  final yet: the run waits.
* **After n**, two counting seats with the same final are enough when the third is silent. A seat
  that answered without a final isn't silent, so that is a disagreement, not a score.
* **The hour-24 void** comes only from start + n, and only when no seat that answers shows a final.
  At least two counting seats must answer, the after-n count, since a void is never taken inside
  the window.
* **A disagreement** is either of two things. Any two finals that differ, from any seat, at any
  hour. Or, after n, finals beside answers without one. The first run that sees it builds the
  dispute record, with every reading.
* **Day 7** counts from the dispute record. Each seat's latest reading counts: fresh if it answers,
  otherwise the one the record carried. The game settles only when four sources are on record,
  none silent, and at least three give the same final. Anything else voids.
* **The spare** (seat 4) is asked on every run.
  * Its final counts toward a disagreement like any other seat's.
  * Its answer without a final never blocks a score.
  * It **stands in for seat 3 for a game whose seat 3 is silent for the whole game**: a game
    created without a usable seat 3 hint, or one whose start report doesn't show seat 3 passed its
    board check. Then seats 1, 2 and 4 count, inside n and after.
  * A seat silent on one run is just silent on that run; the spare does not stand in for it.

## The start

[`src/verify.ts`](src/verify.ts) is the start's rule, written once at verification. It is
proposed on the PR; three of its parts are ruled.

* **Seats 1 and 2** must each list the game by team, within a day of the creator's date either way:
  the games set's `START_BOUND`, a fixed 24 hours whatever the game's n, and the only range it
  accepts a start in. Among records of the two teams, the one nearest the date is the game.
* **The times.** Their two times must lie within an hour of each other (`START_SPREAD`).
* **Seat 3's check.** Seat 3's hint is checked against its board
  ([`src/readers/board3.ts`](src/readers/board3.ts)): the same two teams, the game's home and
  away, at a time within the hour.
  * A hint that fails makes seat 3 silent for the game, never wrong, and the spare must then list
    the game within the hour.
  * A board that can't be read this time makes the run wait.
* **The start written** is the earliest of the counting seats' scheduled times. The spare's time
  never sets it.
* **Otherwise** nothing is written, and a later run tries again.

## One run

[`src/program.ts`](src/program.ts) takes the game as the chain holds it, the run's clock, a
transport, each seat's key and the payout address.

* **By status.** An unverified game goes through verification. A verified game is read in its
  window and decided by the rule at the run's hour. A disputed game waits for its day-7 clock.
  A game that has ended takes nothing.
* **What it returns:** its decision and the report ([`src/report.ts`](src/report.ts), the games
  set's `Report`, enum numbers included). A wait returns no report.
* **What a key and the payout can do.** A key decides only whether its own seat can be asked; a
  missing key is a silent seat on that run. The payout lands in the report's payout field and
  nowhere else.

## The cases record

`cases/` holds odd games, one JSON file each, by seat. Each file has:

* the game as the chain holds it;
* the run's clock;
* the exact payloads the run rests on: seat, path and SHA-256 of a saved answer under `fixtures/`;
* the outcome, and why.

`test/cases-record.test.ts` replays every case with those payloads and nothing else. A case
fails when:

* a payload's bytes change;
* the run asks for something the case doesn't list, or stops asking for something it does;
* the outcome differs.

The public cases record lives in ospex-artifacts. To pin a new odd game, save its payloads under
`fixtures/` and add a case here.

## Running

```bash
bun install --frozen-lockfile
bun test          # no key, no network: every answer comes from fixtures/
bun run typecheck # src/ loads no runtime types, so it cannot name process, fetch or Bun
```

To see one game read, seat by seat, from the saved answers:

```bash
bun run replay --list                                  # the saved cases and their clocks
bun run replay --case "mlb doubleheader, game 1"       # one case, at its own clock
bun run replay --game game.json --at 2026-10-23T03:32:00Z
```

A game file holds what the chain holds for a game: `league`, `home`, `away`, `start` (an ISO time
with its zone, or unix seconds), `n` in seconds, and `hints` (`[{ "seat": 3, "id": "..." }]`).
A request the saved answers don't hold is listed, and that seat reads silent.

Rebuilding the workflow id from source is in [`../BUILD.md`](../BUILD.md).

## Fixtures

`fixtures/` holds the feeds' answers exactly as they came back, one file per request, and
`fixtures/index.json` records each one's seat, path, status, size, SHA-256 and capture time. The
index keeps paths, never hosts or keys. A test checks every file against its hash, so an edit or a
line-ending conversion fails the suite; `.gitattributes` marks the folder `-text` for that reason.

A request asked more than once keeps every answer. Each test case reads at its own clock and is
served the latest answer captured at or before it (to the second), so one game can be read not
final at one clock and final at a later one, by the same requests, and a league a seat once
refused reads `http 401` at the clock of the refusal and answers at a later one.

## Re-running the capture

With each seat's key in `OSPEX_SEAT1_KEY` to `OSPEX_SEAT4_KEY`:

```bash
bun capture/capture.ts <plan.json>   # runs the readers live and saves what they ask for
bun capture/teams.ts                 # rebuilds src/teams/ from the saved team lists
```

The capture never prints or saves a key. It paces each seat to its plan and prints the calls it
made.
