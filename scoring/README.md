# scoring

The v3 scoring program. For one game, it reads each of the four feeds and says, feed by feed,
whether the feed was silent, answered without a final, or answered with a final and its two
scores. Then it decides by one fixed rule what those readings add up to: a start, a score, the
hour-24 void, a dispute record, a day-7 result, or nothing yet. It builds the one report shape
the games set takes. This folder imports nothing from Chainlink, so the Chainlink workflow and
the open path's sealed machine run the same files. Its entry point is `src/program.ts`.

## The feed table

[`src/table.ts`](src/table.ts) is the one file that names a feed. Everywhere else, in the
code, the fixtures, the tests and every reading, a feed is its seat:

| Seat | Role |
|---|---|
| 1 | counts |
| 2 | counts |
| 3 | counts |
| 4 | the spare, asked on every run |

A feed keeps its seat in every league. Six leagues are offered (`nfl`, `nba`, `mlb`, `nhl`,
`ncaaf`, `ncaab`), each with all four seats. Nothing here shows that the four feeds draw on
independent sources upstream: agreement across seats guards against one feed's error, not against
an error several feeds copied from one source. The table is frozen at load and is part of the
program's fingerprint. The only things handed in at runtime are the game (read from the chain),
the run's clock, a transport, and each seat's key; a test shows that none of them changes which
seats are asked.

## How a game is read

Seats 1, 2 and 4 are read by team and window, each asked for the one game: seat 1 for the two
teams' games on the window's filing dates by its own ids for the teams, seat 2 for each team's
games over those dates by its own spelling of the team, the spare for the game by its own id when
the creation hints carry one, else for its slate of live, upcoming and recent games (it cannot be
asked by team) where the league's slate fits the size a run's answer may be: college basketball's
does not, so a game there created without the spare's id is not asked for at the spare. An id the
feed answers nothing for, or whose row is not the game, falls back to the slate the same way.
Neither seat 1 nor seat 2 is ever asked for a day's slate: one game's read costs one request at
seat 1 and two at seat 2 whatever the league, and a slate page of college games is past the size a
run's answer may be. Seat 3 is read by its creation hint: its results carry points and status but
no team names and no game time, and its board, which has both and is asked for the hint's row by
its id, drops a game once the game is final, so the hint is the only thing that ties a result to a
game.

* **By team.** A feed's record is the game only when its two teams resolve to the game's two
  teams, in either order. Points come back by team, never by the feed's home or away slot, so a
  feed that lists the teams the other way round still reads right. Every name a feed gives a team
  must resolve to that one team; a name the lists don't know, beside one they do, leaves the team
  unresolved. No reader takes a city as a team's name. A conference missing or null on a college
  team, or any other missing metadata, is unknown and never a mark against the team: the record
  still binds by its names and time.
* **The team lists** ([`src/teams/`](src/teams)) are generated by `capture/teams.ts`. A spelling is
  an alias only when a seat's own list carries it (the team lists of seats 1, 2 and 4, and seat 3's
  board) and one reviewed identity joins it to exactly one team: the team's own name on seat 1's
  list, or a hand join in `capture/joins.json`, grouped by seat and league with the reason each
  group's spellings are that team. Each team also carries how seats 1 and 2 are asked for its
  games (`ask`): seat 1's own id for it, and seat 2's own spelling, taken from those lists and
  never typed in; a team seat 2's list lacks (most college football schools) is not asked for
  there, and a game of two such teams leaves seat 2 silent without a request. Nothing shortens a name to make it match: "Colorado College" is
  not the Colorado Buffaloes. A name that matches no team, or two, joins nothing, and so does a name
  a school outside the league's teams also carries on seat 1's list, with one reviewed exception
  (Georgia, whose namesake there is not a school). College football and basketball share each
  school's spellings. `capture/teams-report.txt` lists every hand join and every name that joined
  nothing. A league's teams are seat 1's current entries: every team on its NFL and MLB lists; on
  its NBA and NHL lists, the teams with a current conference (the lists also carry defunct and
  overseas teams); in college basketball, the Division I schools (the entries with a conference);
  in college football, every entry that names a school.
* **The window.** A record counts only if the feed's own game time for it is inside
  `[start, start + n)`, the game's n and nothing else. The start instant is in; the end is open,
  so a game at the same clock time the next day is out. The start is the scheduled start, taken
  from the counting seats when the game is verified; seat 4's own time is the actual start, which
  only ever serves seat 4's own window check.
* **Only one.** Without a hint that names it, a record is the game only when nothing else in the
  answer could be: no other record of the two teams inside the window (a doubleheader, or the next
  game of a series), no record inside the window with one of the game's teams beside a name the
  lists don't know, no such record without a game time, and no record the lists can't place inside
  the window and earlier than it. Otherwise the seat is silent. A record the lists can't place has
  neither side resolved (names the lists don't know). Earlier in the window, it may be the game
  itself, listed in a way the lists don't know, and the record after it the two teams' next game. At
  the same instant or later, or with no time, it doesn't stop the read. A record whose two names
  both fail to resolve, inside the window, could be the game respelt: the seat is silent.
* **Hints, seats 1, 2 and 4.** A creation hint names a feed's own id for the game, and only chooses
  among records that pass both tests above: the game's two teams, and a time inside the window. A
  hinted record that passes both is read, whatever else is in the window; one that fails either is
  never read. A hint the feed doesn't have, or one under other teams, is dropped, and the game is
  found by its teams. A hinted record of the two teams outside the window leaves the seat silent
  while anything inside the window could be the game, and otherwise is dropped too. Two different
  hints for one seat leave it silent. In a doubleheader or a series, a hint is what lets a seat
  choose between the games inside the window; verification holds a hint at seats 1 and 2 to the
  record nearest the creator's date (The start, below). The spare asked by its id reads the hinted
  record when it is the game's two teams inside the window; an id the feed answers nothing for, or
  whose row is not the game, is unusable, and the slate then decides as it would without the id, in
  one more request, where the league's slate fits the size an answer may be (`SLATE_FITS` in
  [`src/readers/seat4.ts`](src/readers/seat4.ts)); where it does not, the seat is silent.
* **Seat 3, by hint.** One request: the feed's result for the game's seat 3 id. The hint rides in
  the creation event on chain, so anyone can re-run the match while the feed answers for that id:
  in the answers saved on 22 Oct, a result about four days old answered, and ids 78 to 156 days
  old answered nothing (the feed says five days). With no team names or time to read, seat 3's
  points are the feed's own home and away, bound to the game by the hint; checking that binding
  against the feed's board while the game is listed belongs to verification. No hint, two
  different hints, or a hint that is not a seat 3 id, and seat 3 is silent without asking. A
  result's id is held to the same shape, the feed's UUID: a result whose id is not a seat 3 id
  (missing, empty, a number, `"0"`) is a result without a usable id, an answer the reader could not
  use, the line carrying the id (`result without a usable id: "0"`); a result under another seat 3
  id is absence, by design: with no team names or time in a result, a row under another valid id
  cannot be told from another game, and the hint is the binding, so a void through seat 3 needs the
  other two counting seats stale beside seat 3 re-keyed.
* **Final or not.** Each reader maps its feed's status to final or not final, and a final also
  needs the feed's own sign of a whole game: at seats 1 and 2 the period count reached the league's
  regulation (or, where seat 1 fills in no period count, every quarter scored); at seat 3
  `FinalType` "Finished"; at seat 4 `completed`. A record that says final short of that reads
  silent: neither a final the reader can take nor a game the feed calls unfinished. Postponed and
  cancelled, in the feed's own words, ride on the reading, and after n a void rests on two counting
  seats' rows that carry one (below); a row scheduled or in play, in a word the reader knows,
  carries none, an answer that is never a void's vote; a row without a readable status is silent, a
  partial row; and a status word the reader does not know is silent too, the word verbatim on the
  reading, so a feed's own word for a lesser case shows in the run's line the first time it happens
  (`unrecognized status "PPD"`); a row the reader can't parse refuses the answer with the game's own
  row's word beside it, whether the bad row came first or second (`unreadable record; the game's row
  says "FINAL"`; at seat 3 the hint's row's `FinalType` and its final flag, `the hint's row says
  "Finished", Final "TRUE"`). Each reader's header says its feed's words.
* **One game under two dates.** A feed can list the same record under two of the dates asked for.
  Identical copies are one record; if the record changed between the two requests, the later answer
  stands when the copies agree on the game's state and differ in their points, a game in play;
  copies that name different teams, or disagree on the state, or where the earlier already said
  final or short of a whole game, are two answers that disagree about the game, and the feed is
  silent.
* **Silent.** A feed is silent when it can't answer about the game: no key, a refused or failed
  request (a 401 from a league the seat's plan does not cover reads `http 401`, so the reason
  travels with the reading), an answer that doesn't parse, a record with no game time, a final
  without points or short of a whole game, more than one record that could be the game, two
  different hints, an answer that came back empty, a listing that does not give the game (absent
  from it, or the two teams' record outside the window), a row without a readable status, a closed
  seat (below), a clock that isn't a number, and, at seat 3, no usable hint, no result for it, or a
  hint naming a row for part of the game. **An irreversible end never rests on fewer than two
  counting seats' affirmative answers, and the void's silence is only clean silence.** An affirmative
  answer is the game's own row, bound by its ids or names and time, that says in the feed's own
  words what became of the game: a final, or that it will not or did not play, postponed or
  cancelled and nothing else. Every reading says what the reader did with the answer (`answer` in
  [`src/types.ts`](src/types.ts)): a seat is silent to the void only when its answer held nothing of
  the game: the body was empty (an empty list, or no result for the id), or was a readable list of
  rows none of which is the game by id or by its names and time, or the request failed, whatever
  its status, with no list holding the game's row in its body, or the seat was never asked or is
  past its window by date arithmetic. Status decides nothing; the body does
  ([`src/readers/request.ts`](src/readers/request.ts)): a 2xx body is read by these rules whatever
  its status; a status outside 2xx is a failure, clean, unless its body is the feed's list and that
  list, read by the one reading a 2xx list gets (its rows, then the pick; there is no second
  parser), is anything but clean silence: a row the reading cannot parse, or any row for the game,
  makes it an answer the reader could not use, exactly as under a 200 (`after n: seat 3 answered
  but could not be used: the game's row in a 503; result without an id`); an error object, a page
  or an empty body on any status is a failure, so a rate limit does not turn a rainout into a
  seven-day wait. The class is
  per seat and the worst of its reads, so the spare's id answer the reader could not use survives a
  clean or empty slate. A non-empty body that is not the feed's list (a single object, a wrong
  envelope), a by-id answer that is not the requested game (seat 3's row without a usable id, the
  spare's row under another id where no slate stands behind it), and any row for the game of any
  shape are answers the reader could not use. Every
  other reading that is not an affirmative row holds the void, whatever the word was: a row of the
  game the reader could not use for a score (no usable id, no status word, a word it does not
  recognize, a final without points, a short final, a finished part of the game), a row it could not
  read at all, a failure or its own cap partway through the seat's reads after rows arrived, two rows
  that could be the game (a hint picks which to score, and does not clear the anomaly for the void),
  two answers at one seat that disagree about the game; the run waits, its line naming the seat and
  the class (`after n: seat 3 answered but could not be used: duplicate result`). Absence is silence
  everywhere: a game not in an answer, empty or not, says nothing, since a spelling the feed no
  longer uses, a filter it did not apply or a list that stops short answers that way too; and a row
  without a status says nothing of the game's end, silence to a score ([`test/never-affirmative.test.ts`](test/never-affirmative.test.ts),
  with its breaks in the header: absence read as an answer again in [`src/pick.ts`](src/pick.ts),
  the void's count taken from any answer in [`src/rule.ts`](src/rule.ts), a bare result read as an
  answer in `src/readers/seat3.ts`; and in [`test/never-void.test.ts`](test/never-void.test.ts), the
  class ignored by the void in `src/rule.ts`, a reader's cap or a throw after rows arrived read as
  clean silence in `src/run.ts`, a failed answer holding the game's row declared clean in
  `src/readers/request.ts`, a failed body's unusable reading dropped to clean there, a result id of
  any shape accepted in `src/readers/seat3.ts`, and a line written without the redaction in
  `src/line.ts`). So a
  spelling seat 2 no longer uses for a team leaves the seat
  silent for that team's games until the lists are regenerated, while one team respelt still
  reaches the seat through the other team's answer and reads as a name the lists don't know. The
  spare past the feed's three-day window is silent by its own date arithmetic, with no request
  sent. Silent is never turned into "no final". A final without points, or one short of a whole game, is silent, an answer the reader
  could not use: scoring never counts it, verification writes no start on it, and the void waits on it.
* **The line.** No line carries the query key, raw or escaped, or any feed string that is not a short
  plain word; the header keys the platform fills are never the workflow's to hold and are protected by
  the word rule ([`src/line.ts`](src/line.ts), the one function every line goes through before it is
  written, and every `why` before it leaves the program; the wrapper's lines and the creation handler's
  rethrown error go through it too). The readers put every feed string on a reading through one quoting
  helper, so it stands in double quotes. A short plain word is 16 characters or fewer of letters,
  digits, spaces and `/ : . -`, never a URL; anything else becomes `[not a status word]`, and so does a
  run outside the quotes carrying `://`, `?` or `=`. Every configured secret value is redacted wherever
  it appears, compared as the decoded word, so a key holding `"` or `\` is found escaped too. A header
  key that is itself a short plain word would stand: the residual this rule accepts
  ([`test/line.test.ts`](test/line.test.ts), [`test/status.test.ts`](test/status.test.ts), and
  [`../games/line.test.ts`](../games/line.test.ts) at the handlers' own log calls; the breaks are in
  their headers and in [`test/never-void.test.ts`](test/never-void.test.ts)'s).

## Open and closed: how long each seat is asked

A seat is open while the program still asks it about a game, and closed once it stops. It closes
at the end of the window its own docs give for a game it keeps (`OPEN_FOR` in
[`src/rule.ts`](src/rule.ts), inside the fingerprint), at a disputed game's day 7, and when the
game is scored. A closed seat isn't asked again, its key isn't needed, and nothing it says later is
read.

| Seat | What its docs say | Open until |
|---|---|---|
| 1 | past seasons' games kept | the game ends (day 7 at the latest for a disputed game) |
| 2 | seasons since 2018 served through the API | the game ends (day 7 at the latest for a disputed game) |
| 3 | a result kept five days from the game's start | five days after the start |
| 4 | completed games kept three days | 66 hours after the start: three days less a margin, since the docs don't say how the three are counted |

The saved answers agree: seats 1 and 2 answered dates 217 days old in full, seat 3 answered
nothing for ids 78 to 156 days old. On a disputed game's day-7 run every seat is closed, and none
is asked.

## Requests per game

One read of one game, whatever the league: seat 1 asks once (the two teams' games on the window's
filing dates, one page); seat 2 once per team, two (one where its list lacks a team); seat 3 once,
or not at all without a hint or past five days; seat 4 once by its id when it has one (two credits
on its plan), else once for its slate where the league's fits, or not at all (college basketball
without the id; past 66 hours): 5 for a scoring run, 6 behind an id the feed answers nothing for
with the slate behind it, the most a full read is admitted on. A verification reads seats 1, 2 and
4 over the range (1 + 2 + 1), seat 3's board for the hint's row (1), its result where the board has
no row for the hint (1), then every seat again in the window from the start chosen, whose dates
differ (1 + 2 more at seats 1 and 2, seat 3's result where it counts, the spare from memory): 9, 10
behind such an id, the most. A disputed game's day-7 run asks nothing. The cap is 12 requests per seat per
game (`MAX_REQUESTS` in `src/run.ts`), reached only by a feed that pages past what one game's
answer should hold; the readers assume a team's games on a window's dates fit one page of a
hundred rows. Each game is read on its own: a slate of games costs the sum.

## What the readings decide

[`src/rule.ts`](src/rule.ts) holds the agreement rule, and every count in it is a constant
inside the fingerprint. For a game whose start is written:

* **Inside n**, every counting seat answers with a final, and the finals are the same: the same
  points for both teams. A silent counting seat blocks. So does one that hasn't answered with a
  final yet: the run waits.
* **After n**, two counting seats with the same final score, over any single answer at the third
  that is not a competing final: in play, a word the reader does not know, an answer it could not
  use, postponed, cancelled. That answer neither votes nor disputes.
* **The hour-24 void** comes only from start + n, and is held to the finals' count: two counting
  seats or more answer affirmatively that the game will not or did not play (the game's own row,
  bound by its ids or names and time, whose status in the feed's own words is postponed or
  cancelled, and nothing else: seat 1's flag and its `postponed` and `canceled`, seat 2's
  `postponed` and `canceled`, seat 3's `FinalType` Postponed and Canceled), the rest of the
  counting seats are silent, and the void's silence is only clean silence (above): a seat whose
  answer touched the game and could not be used, or whose hint chose the game's row beside another
  that could be it, holds the void, the run waiting with its line naming the seat and the class
  (`after n: seat 3 answered but could not be used: duplicate result`); a game a feed lists with a
  row the reader cannot use waits for a second feed's word, a final, or the games set's own clocks.
  A row that says the game is
  scheduled or in play is not a void's vote, and beside two affirmative answers it holds the void as
  it would hold a score. Fewer than two affirmative answers: the run
  waits every tick, its line saying what each seat gave; the program never ends a game on fewer,
  and the games set's own clocks end a game the feeds never settle.
* **A disagreement** is either of two things. Any two finals that differ, from any seat. Or, after
  n, a lone final against two counting seats that say the game will not or did not play; a lone
  final beside anything else waits for a second. The first run that sees it posts the dispute
  record, with every seat's answer, inside n or after.
* **After the record** the game is not locked, and it is decided on every seat's vote. A seat's
  vote is its most recent answer while it is open, and its last answer once it is closed (above). An answer is a final, or the game's own record shown without one; silence, a
  listing without the game, or the game outside the window leaves a vote where it was, and a
  game shown without a final after a final is a vote of no final.
  * The game scores the moment the votes agree, by the same rule as above, and only on three or
    more votes with that final: a disputed game never settles on fewer than three agreeing
    recorded sources. Two counting seats with the final and the third silent wait for a third,
    the spare's vote included, or for day 7. The score carries the votes it rests on. A 2-2 on the
    record stays a 2-2 until a seat changes its vote.
  * Until then a run posts an update, the same report with every seat's answer, whenever a seat's
    vote changes, and writes nothing otherwise: never per run, and one report however many votes
    change on it. An update credits nothing.
* **Day 7**, counted from the first record, is the deadline for a dispute that never resolves; an
  update never moves it. By then every seat is closed, so day 7 reads every seat's vote on record
  and asks nothing. A seat silent for the whole game is silent here too, whatever
  the record carries for it. The game settles only when four sources have a vote, none silent, and
  at least three give the same final. Anything else voids.
* **A game without a record** is decided on the run's own readings: nothing earlier is on chain.
* **The spare** (seat 4) is asked on every run while it is open.
  * Its final counts toward a disagreement like any other seat's.
  * Its answer without a final never blocks a score.
  * It **stands in for seat 3 for a game whose seat 3 is silent for the whole game**: a game
    created without a usable seat 3 hint, or one whose start report doesn't show seat 3 passed its
    board check. A hint the board no longer lists is read by its result at verification: no result
    for it, or one the reader could not use, stands seat 3 down the same way, and a final there
    writes no start. Then seats 1, 2 and 4 count, inside n and after.
  * A seat silent on one run is just silent on that run; the spare does not stand in for it.

## The start

[`src/verify.ts`](src/verify.ts) is the start's rule, written once at verification.

* **The date says which game.** Seats 1 and 2 are read by team without their hints, a day
  either side of the creator's date, and among records of the two teams the one nearest the date is
  the game. A seat whose hint names a different record makes the run wait. (At scoring, hints still
  choose among the records in the window.) The spare keeps its id: an id present is read by itself,
  never the slate, and its record is the hint's own; where the feed has nothing for the id, the
  slate's where the league's fits, else the spare is silent (`src/readers/seat4.ts`), and scoring
  reads it the same way.
  * A record with a team the lists don't know, one of the game's teams beside a name they don't
    know or a record they can't place, is weighed only where scoring weighs it: in the window from
    the start chosen, when every seat is read again (below). A day before the game it stops nothing.
  * A hint the feed no longer lists, when it reissues the game under a new id, still names another
    record: the run waits, the game ends in the release, and the creator re-creates it. The hint is
    never dropped, since if its record came back inside the window, it would choose it at scoring.
* **Seats 1 and 2** must each list the game by team, within a day of the creator's date either way:
  the games set's `START_BOUND`, a fixed 24 hours whatever the game's n, and the only range it
  accepts a start in.
* **The times.** Their two times must lie within an hour of each other (`START_SPREAD`).
* **Seat 3's check.** Seat 3's hint is checked against its board
  ([`src/readers/board3.ts`](src/readers/board3.ts)): the same two teams, the game's home and
  away, at a time within the hour.
  * A hint that fails makes seat 3 silent for the game, never wrong, and the spare must then list
    the game within the hour. A hinted row for a part of the game (a half, a period) fails.
  * A board that can't be read this time makes the run wait. So does a row of it the program can't
    read: an id that isn't a seat 3 id as a hint must be one (padded, cut short or a number all
    wait), the hint's row without readable teams, or the game's own row without a readable time. A
    row of other teams fails whatever its time says. A side the board names only by a placeholder
    ("TBD") isn't named yet: the row waits, unless the side it does name makes it another game.
  * The board is asked for the hint's row by its id, one path (`POST /odds/bygames`, the id, the
    league's code and the game's odds type in the body; 579 bytes as saved): the row answers, or
    nothing does. A hint it has no row for fails at once, whatever the game's date. The board drops
    a finished game, so before such a hint stands seat 3 down, seat 3's result for it is read: a
    final there writes nothing, and a read that fails waits.
  * With seat 3 counting, the spare, when it lists the game, must list it within the hour of the
    counting seats: scoring reads the spare by that record, and one further off is another game.
* **The start written** is the earliest of the counting seats' scheduled times. The spare's time
  never sets it.
* **Verify the way you'll score.** Before the start is written, every seat is read again as
  scoring's first run will read it: in [start, start + n), with the hints, without the date, seat 3
  by its result when it counts. Each counting seat read by team (seats 1 and 2, and the spare when
  it stands in) must read the record verification found, inside that window, and seat 3, when it
  counts, must read by its result. The spare, counting or not, may read no other record there, and
  a spare with an id must read that record (by the id, or behind an unusable one the slate's, as
  scoring will), or be silent by the feed's answer about the id, nothing for it and no slate behind
  it, which is how scoring will read it too; silent by a read that failed, its hint is unchecked
  and the run waits. A hinted spare that doesn't count and whose record is within the hour of the
  start, a second before the window included, is the game. An unhinted spare that doesn't count
  and is silent at the re-read passes: nothing binds it, and the most it can cost is a dispute.
* **Never a finished game.** While any reading verification takes shows the game final, near the
  date or at the re-read, seat 3's result and the spare read by its hint included, nothing is
  written; and the same for a feed that says the game is finished without points, or with a count
  short of a whole game. A game every seat shows still in play gets its start, late.
* **Otherwise** nothing is written, and a later run tries again.

## One run

[`src/program.ts`](src/program.ts) takes the game as the chain holds it, the run's clock, a
transport, each seat's key and the payout address.

* **By status.** An unverified game goes through verification. A verified game is read in its
  window and decided by the rule at the run's hour. A disputed game is read the same way on every
  run, and scores, posts an update, or reaches day 7 (above). A game that has ended takes nothing.
* **What it returns:** its decision and the report ([`src/report.ts`](src/report.ts), the games
  set's `Report`, enum numbers included). A wait returns no report.
* **What a key and the payout can do.** A key decides only whether the run can read at all. A
  seat whose key is missing, or isn't text a request carries as given (visible ASCII, no space; and
  for seat 4, whose key goes in the query, one query value as given: letters, digits and
  `-_.!~*'()`), decides nothing, before any request is sent, and so does a seat whose feed refuses
  the key (400, 401, 402, 403 or 429). It is never read as a silent seat, which would let a key
  choose between a score, a dispute and a void. A seat the run never asks needs no key: seat 3 when
  it is silent for the game, a closed seat, and every seat on a disputed game's day-7 run. The payout lands in the report's payout field and nowhere else, and is refused
  where the games set would refuse it: address 0, the reserved range up to 0xffff, the games set's
  own address, its coin's, and any address ever approved as a reporter (read from the chain).
* **The start report.** A verified game decides nothing unless its start report holds one reading
  per seat, in seat order, with seats 1 and 2 answering: which seats count rests on it.

## Known shapes

Shapes the program reads in a way that is accepted, kept here so they are not rediscovered:

* **The same two teams twice near the date.** When a feed lists the game at the creator's date in
  a way the lists can't place, and the same two teams again hours later as the lists spell them,
  verification reads the later listing as the game and writes its time; the games set takes it,
  since it is within a day of the date. Hints tell the two apart, and are what a creator gives in
  the one sport where two teams meet twice in a day.

## The cases record

`cases/` holds odd games, one JSON file each, by seat. Each file has:

* the game as the chain holds it;
* the run's clock;
* the exact payloads the run rests on: seat, path and SHA-256 of a saved answer under `fixtures/`;
* the outcome, and why.

`test/cases-record.test.ts` replays every case with those payloads and nothing else. A case
fails when:

* a payload's bytes change;
* the run asks for something the case doesn't list, or stops asking for something it does;
* the outcome differs.

The public cases record lives in ospex-artifacts. To pin a new odd game, save its payloads under
`fixtures/` and add a case here.

## Running

```bash
bun install --frozen-lockfile
bun test          # no key, no network: every answer comes from fixtures/
bun run typecheck # src/ loads no runtime types, so it cannot name process, fetch or Bun
```

To see one game read, seat by seat, from the saved answers:

```bash
bun run replay --list                                  # the saved cases and their clocks
bun run replay --case "mlb doubleheader, game 1"       # one case, at its own clock
bun run replay --game game.json --at 2026-10-23T03:32:00Z
```

Verification on the saved answers of college basketball's opening night, 2 to 4 Nov (every
Division I game seat 2 lists, each created at its own time with no hints):

```bash
bun opening-night.ts            # the counts
bun opening-night.ts --ledger   # and every game, with what verification decides
```

A game file holds what the chain holds for a game: `league`, `home`, `away`, `start` (an ISO time
with its zone, or unix seconds), `n` in seconds, and `hints` (`[{ "seat": 3, "id": "..." }]`).
A request the saved answers don't hold is listed, and that seat reads silent.

Rebuilding the workflow id from source is in [`../BUILD.md`](../BUILD.md).

## Every report it can send

[`shapes/emitted.json`](shapes/emitted.json) lists every report shape the program can send, each
once, for the games set's own tests to run through its report door. Each entry is the report's kind
and points and its four readings, each as `[seat, kind, home, away]`, with the clock it was decided
at (verification, inside the window, after the window, hour 24 or day 7), the status of the game it
meets, the decision and the program's own reason.

[`shapes.ts`](shapes.ts) builds it from the program's own decisions:
* verification, on what the readers can return near the creator's date;
* a game with no record, inside the window and after it;
* and, from every first record those runs post, every run after it, through day 7, each update
  written to the record the next run reads.

So every record a run reads there is one the program wrote. The values are the sweep's: two
finals, 27-20 and 20-27, and an answer without a final at 27-20. A report with three or four
different finals, which only a dispute record, an update or a day-7 void can carry, is not listed.

```bash
bun shapes.ts           # rebuild it after any change to what the program decides
bun shapes.ts --check   # exit 1 if it is stale; the suite fails too (test/shapes.test.ts)
bun shapes.ts --sweep   # and the sweep of a disputed game, every fresh state beside every record a
                        # seat could hold: 1,500,000 decisions, some on records no run writes
```

## Fixtures

`fixtures/` holds the feeds' answers exactly as they came back, one file per request, and
`fixtures/index.json` records each one's seat, path, status, size, SHA-256 and capture time. The
index keeps paths, never hosts or keys. A test checks every file against its hash, so an edit or a
line-ending conversion fails the suite; `.gitattributes` marks the folder `-text` for that reason.

A request asked more than once keeps every answer. Each test case reads at its own clock and is
served the latest answer captured at or before it (to the second), so one game can be read not
final at one clock and final at a later one, by the same requests, and a league a seat once
refused reads `http 401` at the clock of the refusal and answers at a later one.

## Re-running the capture

With each seat's key in `OSPEX_SEAT1_KEY` to `OSPEX_SEAT4_KEY`:

```bash
bun capture/capture.ts <plan.json>   # runs the readers live and saves what they ask for
bun capture/teams.ts                 # rebuilds src/teams/ from the saved team lists
```

The capture never prints or saves a key. It paces each seat to its plan and prints the calls it
made.
